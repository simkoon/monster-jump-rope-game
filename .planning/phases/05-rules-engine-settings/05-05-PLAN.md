## Scope rationale — 31 files in one plan is intentional (plan-checker scope_sanity warning acknowledged)

이 계획은 나누지 않는다. 판단 근거와 위험 통제는 아래와 같다.

1. **원자적 교체가 빌드 구조상 강제된다.** `tsconfig.app.json`은 `src` 전체(테스트 포함)를 타입 검사하고 CI 배포는 `npm run build`(= `tsc -b`)만 돌린다. v1 `types.ts`/`engine.ts`가 사라지는 순간 그것을 import하던 23개 파일이 한꺼번에 깨진다(RESEARCH Pattern 8). 계획 경계는 반드시 green이어야 하므로 삭제와 v1 타입을 쓰던 모든 화면 재작성이 같은 계획에 있어야 한다. RESEARCH가 제시한 "C1 harness+삭제+최소 UI / C2 UI 다듬기" 분할도 C1 끝에서 green이어야 해서 결국 모든 화면을 다시 써야 한다. 여기 화면은 이미 애니메이션 없는 최소 임시 DOM(D-26)이라 C1이 이 계획과 같아지고 C2는 빈 계획이 된다.
2. **실제 작성 부담은 약 15개 파일이다.** 31개 중 14개는 `git rm` 한 줄로 끝나는 삭제이고, CSS 2개는 지우기만 하는 정리다. 남은 작업은 하위 시스템별 3개 태스크(하네스+setup / 플레이 화면 / 시작·결과 화면+App)로 나뉘고 태스크마다 `read_first`가 따로 있다. 순수 부품(엔진 FSM, labels, AnimalPicker, Scoreboard, RingStrip)은 05-02~05-04가 이미 만들었으므로 이 계획은 배선 위주다.
3. **알려진 타입 오류 구간은 Task 1 커밋 ~ Task 3 완료 사이로 제한된다.** Task 1 커밋 뒤에는 아직 재작성하지 않은 화면 파일(PlayView, HUD, SetupView, ResultView, App 및 그 테스트)에서만, Task 2 커밋 뒤에는 SetupView·ResultView·shell.test·App·App.test에서만 `npx tsc -b`가 실패한다. 통제 방법:
   - Task 1·2의 `<verify>`는 이미 옮겨진 범위(엔진, 하네스, 설정, 데이터 보존 tripwire, hud)를 vitest로 실제 실행하므로 중간 커밋도 동작이 검증된 상태다.
   - 뒤 태스크 소유 파일의 타입 오류를 앞 태스크에서 임시 스텁·TypeScript 억제 주석·`any` 캐스트로 덮지 않는다. Task 3 acceptance가 `src` 전체에서 억제 주석 0건을 확인한다.
   - Task 1~3 사이에는 push하지 않는다. 이 계획은 Task 3의 `npx tsc -b && npx vitest run && npm run build`가 exit 0일 때만 완료다.
   - 중간에 실행이 멈추면 되돌리지 말고 다음 태스크부터 이어서 진행한다. SUMMARY에 어느 태스크까지 커밋됐는지 기록한다.
