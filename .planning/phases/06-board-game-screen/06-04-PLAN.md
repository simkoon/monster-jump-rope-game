## Scope rationale (checker scope_sanity warning — kept as one plan on purpose)

This plan has 3 `<task>` elements (the `<tasks>` wrapper is not a task) and 14 files, under the 15-file blocker. The file count is high but the context cost is moderate:
- Most files are small presentational parts: 3 new props-only components (StatusChips, Banner, ContextLostOverlay) and 3 existing HUD components rewritten in place; labels.ts only gains pure helpers.
- 5 of the 14 files are tests. Only hud6.test.tsx and labels.test.ts get new cases; hud.test.tsx and tempHud.test.tsx only lose the describes that move to hud6.test.tsx, and App.test.tsx only changes two expected strings.
- PlayView.tsx gets a two-prop change and is deleted in 06-06; game.css is append-only (Task 3, 1 file).
- No task touches more than 8 files (Task 1: 6, Task 2: 8, Task 3: 1), and each task ends with its own green verify.

Why not split into a labels/chips/banner/overlay plan and a scoreboard/turn-bar/controls/CSS plan: both halves write hud6.test.tsx and read the new labels.ts helpers, so the second would have to wait for the first anyway (no parallelism gained), and the split would renumber 06-05/06-06 and every depends_on that points at them. If executor context runs tight, the natural seam is after Task 1 — its output is self-contained and green, and Task 2 starts from the committed files.
